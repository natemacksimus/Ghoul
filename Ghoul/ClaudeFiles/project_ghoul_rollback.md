Rollback netcode implemented (2026-08-18). Builds on [[project-ghoul-multiplayer]] session infrastructure.

**Architecture:**
- NGO stays for session management (Relay, PlayerSpawner, scene loading). Relay is still used for NAT traversal.
- `ClientNetworkTransform` is DISABLED at session start. Rollback drives all positions.
- `RollbackSession` (new) drives the deterministic simulation loop via FixedUpdate.
- Inputs only (10 bytes/frame) are sent over the wire via NGO CustomMessagingManager (Unreliable).
- Last 3 frames bundled per packet for loss recovery (standard fighting-game practice).

**New files — Assets/Scripts/Rollback/:**
- `Fix64.cs` — Q16.16 fixed-point math (groundwork; Controller2D still uses floats for now)
- `FixVec2.cs` — 2D fixed-point vector
- `RollbackInput.cs` — 10-byte input packet (bitmask + 2 analog axes as int16)
- `ISnapshotable.cs` — interface: SaveState(BinaryWriter) / LoadState(BinaryReader)
- `InputCapture.cs` — accumulates Unity Input System events between frames; GetAndClearFrame() called by RollbackSession
- `RollbackSession.cs` — circular buffer (128 frames), prediction (repeat last confirmed), misprediction detection, rollback + re-simulation
- `RollbackSetup.cs` — add to NetworkManager GO; auto-detects spawned players by tag, wires session

**Modified files:**
- `EntityController` — implements ISnapshotable (position, velocity, all state flags, knockback); HandleKnockback/HandleDirectionalKnockback made protected
- `PlayerController` — implements IRollbackSimulated (SimulateFrame); FixedUpdate suppressed when session active; RunFixedStep() extracted as shared body; SaveState/LoadState override
- `PlayerInput` — callbacks route to InputCapture when rollback active, fall through to PlayerController otherwise
- `CharacterStats` — implements ISnapshotable (health, speed, damage, knockback power); InflictDamage applies locally (no RPC) when rollback active

**Determinism note:**
Controller2D still uses floats. On same-platform (Windows→Windows) IEEE 754 is bit-identical so this is acceptable for co-op. Full cross-platform determinism requires migrating Controller2D to Fix64 (follow-up task).

**Unity Editor wiring required:**
1. Add `RollbackSetup` component to the NetworkManager GameObject (or any DontDestroyOnLoad root).
2. Either assign player NetworkObjects in RollbackSetup inspector, OR ensure player prefab is tagged "Player".
3. Ensure `InputCapture` component exists on the player prefab (RollbackSetup adds it automatically if missing).
4. Set NetworkManager Tick Rate to 60 and Unity FixedUpdate to 0.01667 (1/60s).
5. Verify Console is clean on first import — CustomMessagingManager API, FastBufferWriter usage may need iteration.

**NGO systems retired for gameplay (kept for session only):**
- `ClientNetworkTransform` (disabled at session start)
- `netFacingRight` NetworkVariable in EntityController (still present but irrelevant; facing is in snapshot)
- Damage/knockback RPCs in CharacterStats (bypassed when rollback active)

**2026-09-09 desync fixes** (found via local Multiplayer Play Mode playtest — the two instances showed a player at different positions from each other):
1. `RollbackSession.FindEarliestMisprediction()` compared `_remotePredicted[idx]` against the confirmed input even on frames where the remote input was already known at simulation time (no prediction ever made) — `_remotePredicted[idx]` held stale data from `BufSize` (128) frames earlier in that case, so it read as a mismatch almost every tick, forcing a full rollback+resimulation constantly instead of only on real mispredictions. Fixed with a parallel `_wasPredicted[]` array; only frames where a prediction actually happened are checked now.
2. See [[project-ghoul-combat]]'s 2026-09-09 entry — `PlayerAttack` was gated on `IsOwner` and used a coroutine + Physics2D trigger + ClientRpc, all outside the deterministic tick, even though `RollbackSession` simulates both players on both peers. Only the attacker's own machine ever resolved a hit. Now folded fully into the fixed tick as an `ISnapshotable`.
3. Real remote-input confirmation latency through Unity Relay is **~18 frames (~300ms) round-trip, even between two instances on the same machine** — traffic still routes through Relay for NAT traversal, it's never a direct loopback. `maxRollbackFrames` was set to 8 (133ms). `FindEarliestMisprediction()`'s search window is `[CurrentFrame - maxRollbackFrames + 1, ConfirmedFrame]` — once confirmation lag exceeds `maxRollbackFrames`, `oldest` has already moved past `ConfirmedFrame` by the time a late-confirmed frame's real input arrives, so the loop never reaches it. The misprediction is never even checked, let alone corrected — a wrong speculative guess for that frame becomes permanent silently, every time the remote player's real input differs from the repeat-last-input prediction (i.e. constantly, for any actual movement). Fixed by raising `maxRollbackFrames` to 30 (500ms), comfortably above the measured latency.
4. `ConfirmedFrame` was a strictly gapless sequential counter (`AdvanceConfirmedFrame()` only advanced past `-1` if frame 0 specifically was confirmed, then frame 1, etc. with zero gaps). If the very first packet was ever lost — plausible at session start before the remote's message handler finishes registering — it got stuck at `-1` **forever**, even though every later frame's input was arriving and being stored correctly in `_remoteConfirmedFrame[]`/`_remoteInputs[]`. That permanently blinded both `PredictRemoteInput` (always returned blank input) and `FindEarliestMisprediction` (loop range never executed) on the affected peer. Replaced with a simple high-water mark updated directly in `OnRemoteInputReceived` whenever a newly-received frame exceeds it — the existing per-slot `_remoteConfirmedFrame[idx] != f` check already safely skips any real gaps, so no gapless requirement is needed.
5. **The actual remaining root cause**, found by hashing the full serialized snapshot (every `ISnapshotable`, not just position) every 10 frames on both peers and diffing: `Controller2D.collisions.fallingThroughPlatform` (the one-way-platform drop-through flag) was never included in any `SaveState`/`LoadState` — it's set by `VerticalCollisions()` and cleared later by a Unity `Invoke()` callback on **real wall-clock time**, entirely outside the simulation clock. A rollback's `LoadSnapshot` restored every other field to an earlier frame but left this flag at whatever real time had left it at. If it was `true` because the player *later* (in now-rolled-back frames) dropped through a platform, resimulating those earlier frames treated every one-way platform as pass-through and the player fell straight through the level into permanent freefall on one peer only — while the other peer, which never rewound past that point, showed the player standing normally. Fixed by adding `fallingThroughPlatform` and `faceDir` to `EntityController.SaveState`/`LoadState`. The `Invoke()` timer itself is still real-time-driven (a smaller residual risk — its exact firing frame can still jitter by ~1 frame between peers) but no longer causes a wrong value to survive a rewind.
6. Also fixed: `Physics2D.RaycastAll` does not guarantee hit ordering. `Controller2D`'s `HorizontalCollisions`/`VerticalCollisions`/`DescendSlope` process hits in whatever order the query returns them, mutating `moveAmount`/`collisions` cumulatively — added `SortByDistance()` after every `RaycastAll` call so the result depends only on geometry, never on incidental physics-engine ordering (relevant right at multi-collider corners/edges, e.g. landing on a platform edge).
7. Along the way: confirmed via the same logging that Unity's Multiplayer Play Mode virtual player, when configured to run as an actual built Player (shows as `[Player N]`/`[Windows_Build.exe]` in the console, distinct from the untagged main Editor instance), does **not** auto-rebuild on script changes — it must be explicitly rebuilt/relaunched from the Multiplayer Play Mode window after editing scripts, or it silently tests stale code. Cost several rounds of "still broken" reports before this was caught.

**Verified fixed (2026-09-09):** after all six fixes above, a full-state hash comparison (every `ISnapshotable`'s serialized bytes, sampled every 10 frames across ~1080 frames of live co-op movement/jumping) showed `transform.position` for both players bit-identical between peers at every sampled frame, no infinite-freefall recurrence. The hash itself still differs — harmless: `previousXVelocity`/`previousYVelocity` in `EntityController` are written every render-`Update()` (framerate-dependent) but never read back into any computation, so they're inert snapshot noise, not a real divergence.

8. **Combat/knockback-specific desync**, surfaced only once actual attacking + knockback was tested (movement-only testing above never hit this): `PredictRemoteInput()` predicted an unconfirmed frame by copying the *entire* last confirmed `RollbackInput` verbatim, `Buttons` bitmask included. But per `RollbackInput`'s own doc comment, button bits are one-frame rising-edge **events** (a press), not held state — analog axes (Move/Aim) are the only fields meant to be repeated as "last known." If the last confirmed frame happened to have e.g. `BtnUseRight` set (because that's the exact frame it was pressed), every subsequent predicted frame also showed it "pressed" until the real (correctly event-cleared) input was confirmed — re-triggering `PlayerAttack.Attack()` on every predicted frame in the window. Observed directly via temporary per-event logging as `HIT`/`BOUNCE` registering on many consecutive frames (six in a row, seen once) on the peer predicting the attacker, none of that duplication on the peer that owned the swing. Fixed by zeroing `Buttons` in the predicted struct — only the continuous analog state carries forward; a real button event is still picked up exactly once via the normal misprediction-and-rollback path once confirmed. Verified via position+hash logging: brief transient divergence during the attack/bounce window itself (expected — prediction lag), converging to bit-identical position on both peers within ~10 frames and staying converged through repeated subsequent attacks.

**2026-09-09, continued — a slow-building movement-only desync surfaced after all of the above** (took minutes of play to appear, not present in short tests), requiring three more fixes found via the same log-and-diff method:

9. `EntityController.ApplyDirectionalKnockback` (used by `PlayerAttack.CheckHit`) is called *synchronously* from inside `SimulateFrame` — meaning when player 0 (simulated first each tick) hits player 1, it mutates player 1's knockback state directly, before player 1's own `SimulateFrame` call runs later in the *same* tick. This ordering is fixed and consistent (0 then 1, always), so it isn't itself a bug — noted here because it was investigated as a candidate and ruled out.
10. **`Physics2D.autoSyncTransforms` is disabled project-wide** (`ProjectSettings/Physics2DSettings.asset`, `m_AutoSyncTransforms: 0`, presumably for performance). During rollback resimulation, `Controller2D.Move()` calls `transform.Translate()` for both players many times within a single real frame (replaying up to `maxRollbackFrames` frames per correction). Without an explicit sync, a raycast against the *other* player's collider could see a stale, pre-move position until Unity's next natural sync point — making collision against the other player order/timing-dependent instead of a pure function of position. Symptom: the locally-owned, never-predicted player's own position would jitter (small, transient Y dips) specifically during/after heavy resimulation, even though its own input never changed — impossible unless something outside (snapshot, input) was leaking in. Fixed by calling `Physics2D.SyncTransforms()` immediately after every `transform.Translate()` in `Move()`.
11. `Array.Sort` (used by the `SortByDistance` fix from item 6) is **not a stable sort** — two raycast hits at the exact same distance (a flat corner) could still swap relative order unpredictably between peers even with distance as the sort key. Hardened with a deterministic secondary tie-break on the hit `point` coordinates (never object identity/`GetInstanceID` — that's assigned per-process and differs between peers).
12. **The actual remaining root cause of the slow-building desync**: `FindEarliestMisprediction()`'s scan range went up to `ConfirmedFrame`, but `ConfirmedFrame` (a high-water mark, per fix #4) is updated asynchronously as network messages arrive and can legitimately exceed the local peer's own `CurrentFrame` if the remote peer is simply running ahead. Nothing clamped the scan range against `CurrentFrame`, so `FindEarliestMisprediction` could return a `toFrame >= CurrentFrame`. `PerformRollback` would then `LoadSnapshot` a buffer slot that had never actually been simulated yet — stale leftover data from a prior `BufSize`-frame buffer cycle — and its resimulation loop (`for f = toFrame; f < CurrentFrame`) would never execute since `toFrame >= CurrentFrame`, so the corrupted state just sat there, uncorrected. Confirmed directly in logs as `ROLLBACK toFrame=128 currentFrame=125 span=-3` (negative span). Fixed by clamping the scan's upper bound to `Mathf.Min(ConfirmedFrame, CurrentFrame - 1)`.
13. Also found via the same investigation, and fixed for completeness even though not proven to be the corruption's cause: `EntityController.SaveState`/`LoadState` only captured two of `Controller2D.CollisionInfo`'s fields (`fallingThroughPlatform`, `faceDir`, from fix #5). The rest — `slopeAngleOld`, `moveAmountOld`, and the collision flags/slope state — also persist across `Move()` calls (`Reset()` doesn't clear all of them) and feed back into the next collision computation, so any of them could carry a stale, un-rewound value across a rollback boundary the same way `fallingThroughPlatform` did. Now the entire struct is captured.

**Verified fixed (2026-09-09, final pass):** after fixes 9-13, a ~900-frame live movement/jump test showed `transform.position.x` bit-identical between peers at every single sampled frame (only the known/expected sub-second spawn-timing blip at the very start). The only remaining differences were brief Y-axis blips during active jumps — one peer mid-air, the other already landed — each fully resolving within the next sample, which is expected rollback prediction behavior during a fast-changing trajectory, not a bug. Also confirmed the divergence no longer persists after the player stops moving (the previous, broken behavior — checked specifically because a real bug should never resolve just by standing still, while ordinary prediction lag should).

**If more desyncs surface later**, the fastest path back to a diagnosis is the same one used throughout this whole investigation: temporarily re-add (a) a per-N-frame `Debug.Log` in `RollbackSession.TickFrame()` logging `_localPlayerIndex`, `CurrentFrame`, `ConfirmedFrame`, both players' `transform.position`, and a running hash of every `ISnapshotable.SaveState()`'s bytes (N=10 for fast-appearing bugs, N=60 for slow-building ones — check for hours-long sessions if needed); (b) a log in `PerformRollback()` on every call (frame span — watch specifically for a *negative* span, which is the fix-#12 corruption bug if it ever regresses); (c) targeted logs at the specific suspected mutation point (e.g. `PlayerAttack.CheckHit`'s hit branch, `EntityController.ApplyDirectionalKnockback`). Compare the two peers' logs frame-by-frame — the point where position/hash first splits, or where one peer logs an event the other never does, is the bug. Always check whether a divergence resolves once the player stops moving — if it does, it's likely just prediction lag; if it doesn't, it's a real bug. Remember to rebuild/relaunch the Multiplayer Play Mode virtual player after every script change (see below) before each test, or the comparison is worthless.

**Known remaining determinism gap (not yet hit in practice, no live case exists today):** `Controller2D.Move()` collides via `Physics2D.RaycastAll` against the shared, live physics world. Only the two players are in the snapshot/rollback system (`RollbackSetup.CollectFromPlayer` only scans the player GameObjects for `ISnapshotable`/`IRollbackSimulated`). `NpcEntity`/`ResourceNode`/`BuildingEntity` are static at runtime (position only changes via explicit save/restore) so this doesn't currently bite, and `ItemDrop.cs`/`ItemGravity.cs` (which do move every FixedUpdate) aren't actually wired into any live spawn path — `Item.DropIntoWorld()` just teleports `transform.position` once. If either of those becomes live (real drop-and-fall physics, moving NPCs, etc.), any such object will need to join the snapshot system the same way `PlayerAttack` now does, or rollback resimulation can get a different raycast result than the original simulation did for the same confirmed input.
